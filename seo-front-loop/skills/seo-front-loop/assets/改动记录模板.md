# 本次改动的名称

这是写作模板，不是已执行记录。按实际情况填写，标题和格式可调整；未知事实写清楚未知，不从示例推断线上状态，不加 JSON 或 YAML 记忆头部。

## 我们在处理什么

说明站点、页面、历史 URL 和相关旧记录。本次是修复问题、验证优化假设，还是结构性项目？当前做到哪一步，依据是什么？

## 为什么考虑这次修改

写明用户关键词、需求、产品事实、数据证据及反证。相比以前尝试新增了什么条件？哪些仍未核实？

## 具体改了什么，哪些没有改

保留修改前后准确原文。主改动是什么，哪些配套必要，会影响哪些页面、内链两端或共享组件？附完整 Diff 和真实证据链接。说明为什么不是在重做旧方案。

## 执行与上线

写清仓库地址、权限检查结果、改前及改后的完整 commit ID 和提交链接。未提交说明并附 Diff；多个提交各自说明作用；合并改写 ID 时追加对应关系，回滚关联原提交。实际部署的提交另核实，不把提交时间当上线时间。不要记录凭据。

按日期追加实际检查、审查、授权、代码版本与部署回执。明确新版本是否已在线确认；未确认前不开始复查时钟。日期写出时区，未完成的事项不要提前记为已完成。

## 当时约定如何观察

用完整句子写本次复查间隔和最多次数，上线确认后列出检查日期。写清主要指标、保护指标、固定页面/查询范围、基线和数据窗口。说明禁止动哪些范围，以及什么条件允许重新立项。

## 后续复查和更正

每次追加实际检查日期、证据覆盖到哪天、结果、干扰、不确定性、决定和下次条件。漏检如实说明，不能补造结果。

结论变化时指明修改了哪次旧判断及原因，保留原文。组合结果不代表每一成员都经过独立验证。
