# seo-front-loop：记忆与防反复修改协议

版本：v1.3，2026-09-09。本文定义目标存储、检查和恢复行为；受控 SQLite/发布门禁仍待实现。默认由单 Codex 串行工作；独立复核按总体方案第 5 节处理。本版补充可用 Skill 的文件模式边界、冻结周期与用户词表快照。

## 1. 什么应该被记住

至少回答八个问题：

1. 当前线上到底是哪一个版本？
2. 某个页面/字段以前出现过哪些内容与策略？
3. 每次为什么改、依据是什么、从哪个版本改到哪个版本？
4. 哪些改动未部署、正在等待搜索处理、正在观察？
5. 哪些被否决、失败、回滚、没有足够数据？
6. 哪些改动值得保留，其结论适用哪些条件？
7. 哪些资源和查询范围现在不能动？
8. 什么新证据出现时，才允许再次研究或修改？

Codex 官方说明：本地记忆属于辅助回忆层，可能后台生成或延迟更新；必须始终生效的规则应放进 `AGENTS.md` 或版本控制文档。因此不能把“模型记得上次聊天”作为防重复机制。[Codex Memories](https://learn.chatgpt.com/docs/customization/memories)

## 2. 四层记忆

当前已提供 Skill 和只读配置/日期脚本，尚未初始化任何真实站点记忆。无账本服务的单写入者、人工发布试点可采用 [Skill 文件记忆协议](../skills/seo-front-loop/references/protocol.md)；下述受控服务是后续升级目标。二者不能同时成为独立可写的权威账本，迁移时须对账并保留历史；文件协议不声称实现事务锁、权限隔离或自动发布安全。

| 层次 | 保存内容 | 权威性与更新方式 |
| --- | --- | --- |
| 项目规则 | 允许范围、实验流程、事实来源、发布权限引用 | 文档/Git 管理；每轮读取。`AGENTS.md` 是入口，不是数据库 |
| 实验账本 | 版本、变更、锁、提案、部署、评估、禁止和重开条件 | 程序通过受控接口写入；发布准入的权威来源 |
| 证据档案 | 数据快照、线上页面、Diff、检查和部署回执 | 不可变或带修订号；每个结论可回溯 |
| 本轮上下文 | 与当前目标有关的限制、历史和下一步 | 从账本生成，供 Codex 阅读；可重建，不得反向覆盖账本 |

项目根目录里的 `SEO_MEMORY.md` 仅作为生成摘要，不能允许多个 Agent 各自编辑成互相矛盾的记忆。Codex 自带记忆可以记“要到哪里查账本”，不能授权忽略账本的锁。

建议实施后的目录结构：

```text
seo/seo-front-loop/          # 本子项目版本控制的规则和工具
  AGENTS.md                  # 实施阶段再创建的启动入口
  docs/
  harness/
  site-config/               # 不含密钥的站点/资源配置
  prompts/                   # Observe/Decide/Execute/Evaluate 协议

<private-state-dir>/         # 主机上明确配置的持久目录；不是 /tmp
  seo.sqlite                 # 单站点试点可共库，所有实体带 site_id
  evidence/<snapshot_id>/
  artifacts/<experiment_id>/
  context/<run_id>/           # CONTEXT.md 与机器可读 context.json
  backups/                   # 私有备份；可恢复账本和其引用的工件
```

运行状态位置必须写入项目配置，所有任务都指向同一个服务/存储。多个 worktree 不能各带一份独立的活动锁。SQLite 一期只支持单主机服务管理，不放网络共享盘；多主机时迁移到共享数据库服务。

Git 存规则、代码和经检查的报告；原始 GSC 数据、凭据、原始行为和支付数据不进入公共仓库。只向 Codex 提供任务所需的脱敏聚合和公开页面证据。初始未接账户或未初始化账本的状态要明确显示，不能用空历史推断“过去从未修改”。

### 2.1 初次接管：不能伪造历史，也不能无限阻塞

首次接管导入可获取的 Git、部署记录、旧实验和人工已知变更，并记录 `history_known_since`、`coverage` 和无法恢复的缺口。历史不完整的旧记录标 `legacy_unverified`。

如果此前从未建立账本，按已确认的接管范围采集当前线上值、核对没有已知活动实验、记录 `baseline_adopted`，从该边界起强制完整记账。边界之前存在未知历史必须一直保留说明，防重复保证仅覆盖已导入和接管后的记录，不能宣称知道所有过去。

接管后的账本缺失或损坏与“接管前历史未知”不同，前者必须恢复/对账后才能继续写入；不能通过重新 baseline_adopted 清空失败和观察记录。

## 3. 资源身份：防止改个路径就忘掉历史

`site_id` 绑定域名集合、GSC property 和生产环境。`page_id` 是稳定内部 ID，并保存 URL 别名、历史路径、语言和 canonical 关系。301 改路径、文件搬家、组件重命名不能生成一段没有历史的新身份。

对于状态不明的 canonical/别名关系，先标 unresolved，确认后再映射；不能把真正不同的页面粗暴合并。

每次实验的影响范围至少有：

- 页面资源，如 `page:<page_id>`。
- 具体修改点，如 `page:<page_id>:metadata.title`、`content.usage_steps`。
- 共享资源，如 `template:landing`、`component:global-seo`、`navigation:footer`。
- 查询意图集群，如 `intent:humanizer-en-commercial`，并保存固定查询成员和版本。
- 对照页面/组的保护预约，用来保证不被其他实验影响。

改 footer 内链可能影响所有页面；改同一页面不同字段也可能干扰 CTR。第一版观察锁默认锁整页及共享影响范围，而不是仅锁某一行代码。完全无 SEO/用户暴露影响的工程修改经影响检查后可以继续；未知范围不能假装无影响。

### 3.1 每个方案保存一张范围卡

分类及合并规则见 [总体方案第 3 节](PLAN.md#3-seo-工作到底包含什么)。同一条方案记录以下信息，不增加独立工作流：

| 字段 | 含义与限制 |
| --- | --- |
| `work_kind / primary_category` | repair、experiment 或 structural_project；八个主类别之一。分类名不能替代影响检查或洗掉旧历史 |
| `intervention_unit` | 本次完整解决的问题和干预单位，例如“demo 页的一套导出说明”，而非“改三个文件” |
| `primary_edits` | 主改动成员，绑定资源 ID、具体字段/模块、前后版本和策略 |
| `required_supporting_edits` | 必要配套成员及逐项依赖理由；可为空，不能用“顺便优化”作理由 |
| `change_scope / forbidden_changes` | 批准的编辑集合及排除项；编辑集合应等于主改动与配套项的并集，实际 Diff 逐项核对 |
| `impact_resources / impact_evidence` | 实际受影响的页面、链接两端、共享消费者及关系组；保存映射版本、渲染/依赖证据和未知影响 |
| `frozen_resources / measurement_scope` | 冻结资源、处理组、对照、固定查询组及保护口径；冻结包含受影响资源及需保护对照，不能仅锁可编辑字段 |
| `attribution_unit` | single_intervention 或 bundle；规定结论适用于整项干预还是组合，不等于 causal_strength |
| `engineering_acceptance / seo_evaluation` | 工程正确性标准与 SEO 评估计划分开；后者可明确为不可评估并说明原因，不得伪造通过 |
| `review_policy / reviews` | 冻结 interval_days、max_checks（默认 20/3），从 live_verified_at 派生检查点；每次 checkpoint、真实 reviewed_at、数据截止、结论及下次条件 |
| `keyword_config_snapshot / keywords_hash` | 用户原始词表、优先级与页面映射的快照；另存实际采用查询组版本。文件更新不改旧实验群组，也不自动解除保护 |

整组保存 `bundle_id`（组合时）、方案 hash、前后整体快照及成员清单；成员继续进入现有 variants/changes 历史索引，不必另建一套记忆系统。包括没有直接编辑但受影响的页面，用关系边关联这次干预。

冻结范围不能由模型随口缩小。内部链接默认覆盖直接来源和目标；共享导航按消费者展开，相关意图页纳入保护检查。不无限锁整个链接图，但必须记录残余干扰风险。对照被影响时不得继续作为未处理对照。范围扩展使旧许可失效；上线后发现漏项，应补记实际影响并标污染/复核，不能倒改原方案冒充预先批准。

## 4. 权威记录的最小结构

建议表名和字段如下，实际建表可合并相关小表，但这些信息不能丢失。

| 记录 | 必备字段 |
| --- | --- |
| `sites/pages/resources` | 稳定 ID、URL 别名、环境、代码映射、依赖版本、当前已确认线上状态、事实来源 |
| `runs` | run_id、任务种类、状态、输入快照、memory_revision、模型/提示/工具版本、任务游标、预算、next_check_at |
| `evidence` | snapshot_id、来源、采集时间、数据区间、过滤口径、质量/完整性、脱敏状态、工件引用与校验值 |
| `proposals` | proposal_id、假设类型、所需证据、目标版本、历史检查结果、否决原因、重开条件、去重键 |
| `experiments` | experiment_id、版本化范围卡、work_kind、primary_category、工程验收、适用的 SEO 指标/窗口/方法、当前状态、冻结范围、最长期限 |
| `variants` | variant_id、page/resource ID、字段/模块值引用、exact_hash、规范化 hash、strategy_key、父版本、是否实际部署 |
| `changes` | change_id、experiment_id、before/after variant、before/after 值与 Diff 引用、理由、证据、行为类型、执行者 |
| `reservations/leases` | 资源集合、owner、revision、逻辑预约状态；短期工作租约的期限、heartbeat、fencing token |
| `releases` | deploy_intent、幂等键、plan/diff hash、commit、批准与检查记录、deployment_id、线上确认、恢复状态 |
| `assessments` | 基线/后续快照、计算代码版本、方法、效应和区间（可空）、污染、观察结果、因果强度、操作决定 |
| `decisions/rules` | 保留/避免/重开/例外、适用站点页面和条件、正反证、来源实验、状态、到期复核条件、supersedes |
| `events` | 单调序号、event_id、事件类型、entity_id、父事件、时间、操作者、幂等键、payload、工件引用 |

`events` 是追加式审计历史；状态表是与事件在同一数据库事务中更新的当前视图。更正旧判断要追加带 `supersedes` 的新评估，保留原结论。业务代码不能直接删除旧变更以解锁自己。

一次数据库提交原子地完成“查当前 revision→检查冲突→预约/更新状态→写事件”。工件先落盘并校验，然后事务引用；未被引用的工件可稍后清理。JSONL 仅作导出，不能作为第二份独立可写的真相来源。

### 4.1 实验状态与预约释放

运行任务状态与跨多轮的实验状态分开。一次 Codex 任务结束不代表实验结束；实验关闭也不代表页面失去稳定保护。

| 实验状态 | 进入条件 | 允许的后续状态及资源处理 |
| --- | --- | --- |
| `proposed` | 保存假设和证据 | `reserved` 或 `rejected`；尚不持有观察锁 |
| `reserved` | 历史、范围和原子预约成功 | `building` / `cancelled`；有过期检查，不能长期占着不做 |
| `building` | Builder 开始执行 | `reviewing` / `cancelled` / 暂停重试；不允许发布 |
| `reviewing` | 固定 Diff、自动检查与主任务自检；触发独立复核条件时补齐复核 | `ready_to_deploy` 或回到 `building`；记录 review_mode，回去修改使旧审查失效 |
| `ready_to_deploy` | 检查、许可和发布权限齐备 | `deploying` / `cancelled`；等待太久需要重新校验 |
| `deploying` | 已记录 deploy_intent | `awaiting_exposure` 或 `deployment_failed`；不确定则留在对账状态 |
| `awaiting_exposure` | 已确认生产部署及用户可见版本 | 满足预注册暴露/缓冲条件后 `observing`；达上限则转评估关闭 |
| `observing` | 正式观察窗口开始 | 到期 `evaluating`；允许带记录地延长到预设上限；始终保留冻结 |
| `evaluating` | 质量检查与计算已开始 | `closed` 或按既定规则返回等待；评估不能私改冻结规范 |
| `closed` | 结果与操作决定已经原子记账 | 释放活动预约，创建保护期/stable/reopen 条件；新实验必须新立项 |
| `rejected/cancelled` | 候选否决或上线前撤销 | 无未确认部署后才可释放；保留否决和取消原因 |
| `deployment_failed` | 已证明未上线或恢复已确认 | 记录工程失败与释放/重试决定，不记 SEO 方法失败 |

`contaminated`、`interrupted`、`exposure_unknown` 作为关联标记/事件保存，并触发复核；有部署未知状态时不以“关闭实验”为由释放资源。事故恢复完毕并对账后才明确关闭或重启观察。

上表的搜索暴露与正式观察步骤针对 SEO 实验。修复和结构性项目复用发布、对账和记账部分：线上验证与工程验收通过后，可转 `evaluating→closed` 并记 `engineering_result=passed`、`seo_result=not_evaluated`；若需要继续监测搜索效果，保存关联的只读后续评估任务、期限及必要保护，不能因此假装 SEO 已成功。关闭工程工作不解除其他实验持有的锁。

提案/编码预约默认一个工作日检查一次，最长等待由任务配置决定；若确认未部署且任务撤销可以释放。短期租约到期只允许接管，不能自动取消已经开始的观察。数据等待、预算暂停也必须有明确 `next_check_at` 或 `wake_condition`。

## 5. 防止 A→B→C→A 的三道检查

### 5.1 值和版本检查：确定性拒绝

保存修改前后原值和完整祖先链，检查目标值是否：

- 等于当前值：`NO_OP`。
- 等于任何历史部署版本：`REVISIT_ANCESTOR`。
- 对应同一条件下已拒绝/失败的提案：`REPEAT_REJECTED`。
- 只是规范化后相同的排版变化：`COSMETIC_REPEAT`，不计 SEO 实验。

门禁查询全部关联历史，不能只看最近 10/100/500 条。供模型阅读的摘要可以裁剪，确定性拒绝索引必须完整。历史已归档时保留其版本指纹和索引；无法确认完整性时暂停写入，不按“未找到”放行。

规范化只消除明确无语义变化的格式，例如解析后的属性顺序或无关空白；保留大小写、数字、价格、语言、实体和品牌含义。保存算法版本；算法升级不能让旧指纹失去可比性。

### 5.2 策略检查：拦住近义循环

仅用 hash 不够。以下两个 title 可能字符串不同，但重复了同一个策略：

```text
A：AI Humanizer — Clear, Natural Writing
A'：Write Naturally with Our AI Humanizer
```

需要保存 `strategy_key`，例如“自然表达利益点 + 品牌后置”，并记录已实验过的重点：价格、免费承诺、检测承诺、速度、用例、可信度等。编号不能由 Builder 随意重命名来避开历史。

程序使用结构字段、文本近似检索找出疑似历史；主 Codex 在检查阶段结合新旧原值、以前理由和新证据判断是否同一干预。模糊或不确定时输出 `POSSIBLE_STRATEGY_REPEAT`，不得自动放行；若需例外重开，按独立复核规则处理，不能用自检豁免。

相似文本本身不是永久禁令：修正错误产品事实、真正新增功能可能保留大量原文。必须解释具体变化和证据。第一版不承诺用 embedding 或 LLM 完美识别语义循环，靠“疑似阻断 + 有证据重开 + 频率上限”补足。

### 5.3 时间和资源检查：在形成循环之前就阻止

第一版推荐运营默认值：

| 规则 | 行为 |
| --- | --- |
| 页面或影响资源有执行中/待部署/观察中的实验 | 新 SEO 实验不得进入写入阶段 |
| 实验关闭后 14 天保护 | 允许分析，不开启该范围的新 SEO 写入；技术事故另走例外 |
| 结果良好并决定保留 | 标记 stable；保护期结束也不自动允许优化，需新问题和新证据 |
| 同一页面在滚动 90 天内已开始 2 次常规 SEO 实验 | 第 3 次必须重新评估投入和噪声风险，并获独立复核/已有权限下的人工决定 |
| 最长观察期耗尽仍无结论 | 关闭 inconclusive、保留当前正确版本、设置具体重开条件，禁止立即另起近义实验 |

这些数值可按站点调整；时间到期只代表可以检查是否重开，不代表自动排队修改。事故仍计入所有变更历史和污染记录，但不用于阻止必要修复。

## 6. 候选准入伪代码

```text
can_start(candidate, context_revision):
  核验 site/page/resource 身份与完整历史索引
  核验 evidence 有效、非秘密、目标站点和数据口径一致
  核验当前线上状态与源码基线；存在未知 drift 则拒绝
  核验计划、授权范围、工程验收及适用的指标和暴露/观察条件齐备
  按 work_kind 校验条件：优化实验需测量可行性；修复需正确性依据；结构项目需完整依赖与风险审查
  核验主改动、配套理由、实际影响映射、冻结/对照范围；字段数量不能代替影响检查
  查询所有资源预约、观察锁、稳定保护、对照影响和频率限制
  查询全部历史值、部署版本、策略、失败/拒绝提案
  若重复/旧值/新证据不足，拒绝或转显式 reopen 流程
  若需要人工判断的语义冲突尚未解决，暂停
  在事务中检查 revision 未变化，并预约完整影响资源集合
  生成绑定计划版本、基线、资源、历史 revision 的执行许可

can_publish(release):
  重新执行相关检查；不能复用陈旧的 can_start 结果
  核验许可、租约 token、review、tests、plan_hash、diff_hash、commit
  核验真实发布身份具备当前范围的权限
  先记录幂等 deploy_intent，再调用部署入口
  查回执与线上版本，成功后按 work_kind 进入搜索观察或工程验收；不确定则先 reconcile
```

实际的历史门禁必须来自独立的程序逻辑，不是让 LLM 填一个 `history_checked: true`。如果 Agent 具有修改数据库/门禁和直接部署的全部权限，这套机制只能算协作约定，不能声称硬性保障。生产阶段要把记账与发布身份同 Builder 分离，并让 CI 拒绝缺少有效实验许可的 SEO 变更；策略代码自身的修改也要独立审查。

上述是常规准入；已授权事故恢复使用单独的 Incident 许可，绑定错误证据、必要范围、权限依据与受影响实验，不要求等待 SEO 样本或普通观察锁结束。保留恢复前后快照并及时对账；无法走账本时按已有应急协议保存可恢复审计，恢复后补记，不隐瞒缺口。不能仅把 work_kind 改为 repair 就获得应急权限。

## 7. 允许重新修改，但必须明确为什么

重开记录必须绑定原实验和新证据：

- 原版本/原假设是什么，结果和限制是什么？
- 哪个外部或产品条件发生了实质变化？
- 新证据内容是什么，相比旧证据新增了什么？
- 为什么保留当前版本不如重新实验？
- 本次如何避免以前的失败、污染或不可测量问题？
- 是否涉及历史版本回访或已验证失败策略？
- 谁按什么权限允许这次例外，例外仅覆盖哪些资源？

可接受的新依据示例：已核实的产品事实变化；索引故障；新的且持续的搜索意图变化；可复现的转化损害；以前无法测量现在有足够数据。模型换代、换一个提示词、隔了一周、再次抓取同一份网页不算新依据。

历史版本不能直接当普通新优化提交。必须标注 `action_kind`：

- `experiment`：常规新实验。
- `rollback`：恢复到明确可恢复的基线，引用事故或评估证据。
- `retest`：在已变化条件下重新测试历史策略；需要独立复核。
- `correction`：修正已核实的事实或技术错误，关联受影响实验。
- `structural_change`：已单独批准的完整上线、合并或迁移项目，不能伪装为普通小实验。

`work_kind` 表示验证方式，`action_kind` 表示本次动作及历史关系：常规实验通常对应 experiment/experiment，修复对应 repair/correction，结构项目对应 structural_project/structural_change；恢复和重试再明确标 rollback/retest 并引用原记录。字段改名不能豁免适用的权限、范围、历史和复核检查。

正常 B→A 回滚是有目的的恢复，不等同于无意义循环。回滚后 B 仍保留在失败历史中，下一轮不能再以普通提案 A→B。

## 8. 多轮实例

以下为虚构流程，字母只代表某字段的版本，不代表真实 SEO 结果。

| 轮次 | 发生的事情 | 台账与准入结果 |
| --- | --- | --- |
| 第 0 轮 | 对账确认线上是 A | 保存基线 variant A；导入已知历史，记录未知部分 |
| 第 1 轮 | 证据支持 A→B，已发布并确认线上 | 记录 E1、A/B 原值、Diff、部署、观察起点；锁整页和依赖资源 |
| 第 2 轮 | 另一个任务建议 B→C | `ACTIVE_EXPERIMENT`；只更新观测，告诉用户本轮未修改及原因 |
| 第 3 轮 | 观察完成，结果偏正向但因果证据有限 | 可以 retain B，但记 suggestive，不能称“证明 B 导致增长”；标稳定保护 |
| 第 4 轮 | 新任务觉得 A 更简洁 | `REVISIT_ANCESTOR`；没有新证据不修改 |
| 第 5 轮 | 新任务提出 A'，只是 A 的近义改写 | `POSSIBLE_STRATEGY_REPEAT`，复核后拒绝 |
| 第 6 轮 | 产品功能真正改变，提出 B→C | 创建 reopen；证据与范围审核通过后建立 E2，重新保存基线并观察 |
| 第 7 轮 | C 造成已核实的事实错误 | 走 correction/rollback；与当前代码对账后恢复 B 或修正错误，记录 E2 中断 |
| 第 8 轮 | 再次建议 C | 查询历史失败/回滚记录阻断；不能因为换了 experiment_id 而绕过 |

本机制还拦 A→B→C→D 这种永不回头但不停换写法的无效行为：活动锁、稳定保护和修改频率限制同时生效，不能只检测是否回到 A。

## 9. 多 Agent、崩溃和人工干预

### 9.1 短期租约与长期观察锁分开

Builder 的工作租约可过期以便接管，带 fencing token，过期工作者的写入请求必须被拒绝。实验资源预约持续存在，不能因为进程死了、lease 到期、电脑休眠就解除观察冻结。

另一个任务接管前先查未完成 deploy_intent 和实际线上版本。同一资源集合的预约在一次事务中全拿到或全拒绝，避免两个任务互占资源后都无法继续。

### 9.2 部署不是数据库事务

数据库和外部部署不能伪装成一个原子操作。采用“先记部署意图→调用部署→取回执→线上验证→确认状态”：

- 若调用超时，不立刻重复发布；用同一幂等键查询。
- 若部署平台无原生幂等性，以 commit/构建产物指纹和发布记录对账，不能承诺 exactly-once。
- 发现代码已在线但账本未确认，追加 recovered_deployment，恢复观察起点，不再发布一遍。
- 发现未部署则继续相应阶段；状态不确定则保持相关资源冻结。

每次运行保存阶段游标和 next_check_at。未变化的等待不重复研究；达到阶段重试或预算上限时保存 blocked_reason，下一轮只在重试条件满足时继续。

### 9.3 人工或其他发布系统改动

比较上次线上快照、部署记录和当前 Git/线上状态。未知修改写入 external_change；标明可知的作者与时间，不猜测缺失字段。受影响实验标 contaminated/interrupted。不得把人类改动误当 Codex 上轮成果，也不得自动还原它。

回滚采用针对实验的逆向补丁或对应发布平台的受控回退，并以当前生产基线检查是否会覆盖后续工作。单纯把历史文件整个覆盖回来不安全。

## 10. 每轮上下文如何生成

每次开始、上下文压缩后、恢复任务后、写入前都重新查询；即使在同一聊天中也不能只凭记忆执行。

生成的 Context Packet 至少包含：

```text
site_id / product_repo / production_environment
run_id / memory_revision / evidence_snapshot_id
current_live_commit / current_variants
active_experiments / frozen_resources / control_reservations
stable_decisions / failed_and_rejected_patterns
complete_history_index_revision / related_ancestor_variant_ids
current_proposal_history_check / uncertainty_flags
next_due_jobs / known_incidents / external_changes
allowed_next_actions / explicit_block_reasons
source_record_ids / artifact_checksums
```

不能把全部页面历史一次塞进模型上下文。先按稳定 ID 查目标及共享影响范围，再加载相关实验详情；版本与重复检查由完整索引执行。摘要超长时裁剪解释性正文，不裁剪阻断项；阻断集合太大则转按资源分页读取，并证明已经覆盖全部目标。

摘要标 `generated_at` 和 `memory_revision`。写入前 revision 不一致时重查，不能仅给摘要设置一天缓存就跨任务复用。

## 11. 避免错误经验永久固化

经验规则必须保存：来源实验、适用站点/页面类型/查询意图、观察结果、归因强度、正反证、复核条件与状态。状态建议为 candidate / reviewed_local / transferable_candidate / retired。

一次结果好，最多先成为本页面的局部保留理由。不同页面、多次可比验证后才可申请推广；多个报告引用同一个实验只算一份证据。LLM 的 confidence、多 Agent 的赞成票、一次 before/after 上升不够升级为全局规则。

负面结果也要区分：“内容策略不合适”“没有成功部署”“搜索侧未暴露”“样本不足”“有污染”。不能把部署故障学习成“这个 SEO 方法永远无效”。

组合干预记录“整个组合的结果”，其成员只记“参与此组合，独立效果未知”。不能把一次 title+正文组合的正向观察复制成两条被验证成功的规则；反之组合失败也不证明所有成员都无效。重试某成员时查完整组合上下文；可复用的正确基础设施不因曾参与失败组合而永久禁用。

防重复同时检查整体和成员历史：将旧组合改名，或分几轮重放其成员，仍应检出关联祖先与策略。新增必要配套不能掩盖主改动是在重试旧方案。允许有证据的修复/重试，禁止无证据绕过；无结论组合保持当前正确版本，不自动进入“逐成员再改一遍”的循环。

规则到复核日期变为 needs_revalidation，不删除历史，也不自动重新试所有方案。新事实或新结果推翻旧结论时追加 superseding decision，让下一轮知道为什么规则变了。

## 12. 持久化验收

成功标准包括：关闭当前聊天、重启服务、换一个 Codex 任务后，仍能根据同一台账拒绝观察期修改和历史重复；从备份恢复后仍能解析版本、工件与活动锁。所有候选，包括被拒绝和本轮 no_change，都有最小理由记录与去重键。

建议每日私有一致性备份，数据库用在线备份机制而非直接复制运行中的 SQLite 文件；同时覆盖已引用工件，保存校验清单。执行恢复演练，验证孤立引用、schema 版本、事件连续性和活动状态。保留/删除策略服从真实的数据权限要求，不能把“永久记住秘密”当功能。

发生必要的数据删除时保留允许保留的最小审计标记；若删除导致无法证明历史完整，记 memory_incomplete 并限制相关自动写入，而不是声称历史从未存在。
