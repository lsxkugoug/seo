# seo-front-loop：自然语言记忆方案

多项目更新：每个站点的 config、关键词、自然语言记忆和证据归属于独立管理项目目录。开始前先确认项目，含糊时向用户提问；不得把其他项目的历史和词表当本项目事实。目录、凭据隔离与迁移规则以 [项目协议](../skills/seo-front-loop/references/projects.md) 为准。

数据证据由 [tools/collect_metrics.py](../skills/seo-front-loop/tools/collect_metrics.py) 在配置、权限和用户授权满足后采集；首次基线、各实验改前窗口和后续复查分别保存，禁止覆盖。缺配置由 Agent 按 [数据工具说明](../skills/seo-front-loop/references/data-tools.md) 询问用户，密钥不写记忆。工具不自动形成实验结论。

版本：v1.4，2026-09-12。当前决策记忆全部采用 Markdown 自然语言，不要求数据库、实验 JSON、YAML 头部或机器状态表。没有真实站点记忆需要迁移；旧设计可从 Git 基础版本回看，但不是当前执行要求。

## 1. 为什么这样设计

当前是一个主 Agent 串行管理少量改动。最重要的是理解为什么改、以前试过什么、现在为什么不能再改；自然语言适合保存这些上下文，也便于用户检查。数据库不是让 Agent 理解历史的必要条件。

可靠性来自完整原文、证据链接、写前查历史、保留更正过程和单写入者纪律，不来自文件扩展名。自然语言也不能保证绝不漏读或绝无并发，所以不能把“记录了限制”说成程序已经强制执行。

## 2. 当前唯一记忆协议

详细执行规则集中在 [Skill 自然语言协议](../skills/seo-front-loop/references/protocol.md)，本文件说明设计和验收，不另维护一份独立状态。写作起点是 [改动记录模板](../skills/seo-front-loop/assets/改动记录模板.md)，标题可调整，不需要转换为字段。

管理项目 config 中的 SEO_MEMORY_DIR 指向私有持久目录，默认 .seo-memory。同一站点所有任务与 worktree 必须共用该目录，不同站点分别隔离。

- 站点说明.md：站点和产品仓库、部署方式、接管时间、已知历史与缺口。
- 记忆索引.md：当前关注页面、观察限制、下次检查日、正式记录链接；仅作导航。
- 改动记录/：一项改动一份 Markdown，连续追加提案、执行、上线、复查、更正。
- 运行记录/：经授权执行的每轮简短说明，包含读过哪些记录、拒绝了什么和为什么。
- 证据/：原始指标、线上快照、Diff、回执等，可以保留 JSON、CSV、HTML 等合适格式。

状态与结论以原改动记录和证据为依据；索引与原记录矛盾先核对，不选宽松的一项放行。索引可重建，不可替代或删除历史。

## 3. 一份好记忆需要回答什么

1. 在改哪个页面、模块或页面组？关联哪些旧 URL 和旧记录？
2. 为什么改？用户关键词、产品事实、支持和反对证据是什么？
3. 改前和改后的准确原文是什么？大改动的完整 Diff 在哪里？
4. 哪些是主改动，哪些是必要配套？没有改什么，实际影响了谁？
5. 做到哪一步了？代码写完、构建通过、生产部署和线上确认必须分清。
6. 哪个准确时间确认新版本上线，时区是什么，证据和代码版本在哪里？
7. 当时约定多久复查、最多几次？哪些页面和对照不能再动？
8. 用哪些窗口、查询/页面组、主要和保护指标判断，哪些数据未知？
9. 每次复查发现什么？保留、等待、关闭、修复或回滚的理由是什么？
10. 哪种新证据出现才允许重新研究，哪些旧策略不能无依据重试？

不要求同样的标题、状态词或语法，但事实不能模糊。写“上周优化了标题”不够；完整原文和带时区的上线时间不能只存在聊天里。

## 4. 防反复靠读取和决策过程

每轮从站点说明与索引开始，检索并读完所有相关记录，包括失败、拒绝、回滚和已结束实验。页面迁移、文件搬家、组件改名时保留关联，不能因此重置历史。检索命中只是线索，不能只看几条摘要就宣称检查完毕。

改动前在本轮记录中用自然语言回答：旧版本或相同策略以前试过吗？依据是哪几份记录？观察和保留限制是否仍有效？此次有哪些实质新证据？覆盖不明时允许研究，但不新增 SEO 写入。

默认观察期间保护整页及必要共享影响和对照。实验关闭后保护 14 天；保留的稳定版本即使保护期已过，也需新问题和新证据才重开。同页滚动 90 天第三次常规实验需要重新评估并独立复核。数值是运营约定，不是 SEO 定律。

不要只查 A→B→C→A；近义重写、组合改名、拆成多轮重复旧组合、A→B→C→D 的无结论折腾也要识别。必要修复或回滚有明确目的，引用旧记录、证据与授权，不等同于无意义循环。

## 5. 自然语言示例

以下是虚构的写法示例，不是实际上线或效果结论：

> E001 处理首页 title。原文是“原始标题 A”，新文是“候选标题 B”；正文、描述和内链没有改。本次希望改善某个已明确的用户场景表达，证据见所附快照。
>
> 新版于 2026 年 9 月 9 日北京时间 10:00 确认上线，代码版本与回执见附件。当时约定每 20 天复查，最多 3 次，对应 9 月 29 日、10 月 19 日和 11 月 8 日北京时间 10:00。观察期间不再调整首页的 SEO 内容。
>
> 9 月 29 日复查：数据不足以判断，当前没有已知损害，因此保持 B。没有更换标题的理由，下一次沿用 10 月 19 日检查计划。
>
> 后续发现旧判断不完整时，在这里追加实际日期、要纠正的判断与新证据，不能直接删除这次结论。

如果另一个任务想改回 A，先读到上述原文和限制，再判断有无新依据；不是只凭自己觉得 A 更好看。

## 6. 时间与配置变动

当前 config 只决定新实验默认周期。旧记录用完整句子保留当时约定，改配置不追溯生效。用户确实调整旧计划时追加前后约定、理由和授权，保留原日期与数据窗口。

日期计算器只接收 Agent 从原文核实后的明确参数，不读记忆、不提取状态、不决定到期能否改。记录缺时区、存在冲突或未确认上线时先核实。记忆自然语言不需要为计算器改成固定格式。

到期允许“无结论”。搜索处理慢不重置时钟；错过检查如实记漏检；最后无结论则保留正确且无已知损害版本，结束常规等待并设置重开条件。未知部署或未恢复事故先对账，不自动关闭或解除保护。

## 7. 追加、更正、故障与备份

新事实、复查和更正追加带日期的段落。可以更新文件顶部的当前摘要，但须指向最新决定，不能抹掉旧判断。先写正式记录再更新索引；中途中断时依据原记录、证据和备份恢复，不凭索引猜生产状态。

人工/其他系统修改应写明可知的时间、来源和影响；不猜缺失作者，不自动覆盖。回滚对照当前生产基线，保留后续工作；部署超时先查实际版本，不重复发布。

组合结果只属于整体，成员独立贡献未知；不能拆成多条成功经验，也不能因组合失败永久否定每个成员。新证据推翻旧结论时写出变化条件，避免错误经验永久固化。

记忆与证据一起做私有备份并实际验证恢复。忽略 Git 不等于备份。秘密和不必要个人信息不写入记忆；合法删除造成历史缺口时如实说明并限制相关写入。

## 8. 现阶段边界与旧记录迁移

当前只允许一个主写入任务，发布由人工控制。观察限制是执行协议，不是数据库锁；如果定时任务可能重叠，需另配防重叠运行机制，未配置前不能宣称能无人并发运行。此需求不等于必须把记忆迁到数据库。

发现旧结构化记忆时先保留原件，只读转换为 Markdown 并核对记录数量、原值、关联、限制、证据和日期；确定一份新的正式记录后停用旧写入口，不双写。当前项目没有真实状态要迁移，不能生成虚构基线。

配置文件、用户关键词、指标原始数据保持其格式。Skill 发现所需的元数据不属于记忆。本次不初始化实际站点、不创建定时器、不改产品和线上内容。

## 9. 验收方式

换一个任务只给目录和当前用户请求，应能读出原值、当前限制、复查日期及重开条件；不得默认重写。验证历史较长、索引陈旧、日期矛盾、漏检、未知部署、人工修改与复原等场景，详见 [执行手册](RUNBOOK.md)。

脚本单元测试只能证明配置与算术行为，不能证明 Agent 每次都会读全或 SEO 一定增长。上线前仍需在离线虚构记录上演练，再做有权限的小范围试点。

## 仓库与提交记录

config 的 SEO_REPOSITORY_URL 填实际网站源码仓库，目前未确认，暂留空。Agent 先核对本地 remote 与站点对应关系，并通过已有授权检查目标仓库可读；推送另需写权限和用户授权。明文 config 不保存凭据。

自然语言记录关联完整改前/改后 commit ID 与提交链接。未提交明确说明并保存 Diff，不擅自生成提交；多个提交、合并后 ID 变化及回滚都追加对应关系。实际部署提交和线上验证独立记录。commit 不能替代理由、指标和观察限制。完整规则见 [记忆协议](../skills/seo-front-loop/references/protocol.md)。

验收还应覆盖：配置仓库不匹配、无读取/写入权限、未提交、squash 后追溯、多提交混入业务改动、提交已合并但尚未部署、回滚不覆盖其他改动。单元测试仅验证配置格式，不证明真实 GitHub 权限或上述行为已验证。
