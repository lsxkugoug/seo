# seo-front-loop：总体方案

版本：v1.3，2026-09-09。性质：总体 Harness 仍待实施，不代表已经运行或已证明 SEO 收益。本版交付可复用 Skill、只读配置/日期工具与用户关键词入口；复查统一为部署确认后默认第 20/40/60 天。无生产账户连接或自动发布。

## 1. 设计结论与目标

采用“一个 Codex Agent + 少量确定性工具 + 持久化实验账本”。同一个 Codex 默认串行完成读记忆、采集与研究、制定实验、编码、自检、解释结果及记账。是否临时使用子 Agent 由主 Codex 按第 5 节决策，不按流程阶段固定创建 Agent。程序负责计算指标、历史查询、并发控制、发布准入和记账。

对当前单站点、每次一个小实验的规模，串行优先的理由是工作存在前后依赖，保持完整上下文通常比拆分交接更划算。这是本项目的设计选择，不是已经证明单 Agent 在所有任务上更强；大范围独立研究或需要第二视角时仍可委派。

衡量成功的优先顺序：合格自然搜索转化或业务结果、相关自然点击、可解释的实验结果。提案数量、文章数量、提交数量、Agent 数量不作为成功指标。业务归因尚未接通时，明确只能报告流量层面的结果。

对“Codex 一定更有效”的回答是：它有机会提高研究和工程执行质量，但必须通过相同证据集的对照验收；更强模型不会消除 SEO 的噪声、时间滞后和因果归因困难。

第一版控制在一个站点、一个生产写入者、每次最多一个新实验。可以分析多个页面，但不因此要求修改多个页面。稳定页面没有新问题时，保留原状就是合格决策。

## 3. SEO 工作到底包含什么

### 3.1 数据入口

用户方向入口为管理项目的 [seo-keywords.json](../seo-keywords.json)：primary 优先词、secondary 辅助词、excluded 排除方向、page_targets 期望页面映射和 notes。用户词表是研究优先级，不是已证实搜索量或可直接写入的事实；Agent 需报告采用/待核实/不适合及原因，不擅自替换用户原词。按意图映射页面，避免每个近义词新建一页；关键词更新进入未来候选，不能覆盖活动实验已冻结的查询组。具体规则见 [Skill 关键词协议](../skills/seo-front-loop/references/keywords-and-scope.md)。

| 入口 | 主要用途 | 第一版地位 |
| --- | --- | --- |
| [Google Search Console](https://search.google.com/search-console) | 自有站点的点击、展现、CTR、排名、页面索引诊断 | 核心，需授权；效果评估保留原始聚合快照 |
| [Google Analytics](https://analytics.google.com/) | 自然搜索落地页、合格会话、转化 | 推荐；事件定义和渠道归因先校验 |
| [PageSpeed Insights](https://pagespeed.web.dev/) / CrUX | 实验室性能诊断与有数据时的真实用户体验 | 按性能问题调用；没有 CrUX 数据不阻断其他实验 |
| SERP API 与公开竞品页面 | 搜索意图、结果类型、页面内容和展示变化 | 内容/摘要类实验的重要证据，保存地区、语言、设备、时间 |
| 自站 HTML、渲染页面、Sitemap、robots、代码库 | 技术可访问性、内容与代码位置、发布验证 | 核心；线上和本地都检查 |
| PostHog | 产品行为、漏斗、来源 | 可选；旧实现主要是来源事件汇总，不能当成完整转化归因 |
| Stripe | 收款与收入辅助信息 | 可选；全站收入变化不能直接归因给某个 SEO 页面 |
| Search Status Dashboard、Google Trends | 算法事件、季节性和需求变化的背景证据 | 发生异常或复盘时按需检查 |

竞品没有授权时只能看公开内容和搜索结果，不能拿到竞品 GSC、GA4 或真实收入。新方案不要求购买额外 SEO 工具才能启动，也不因可选服务未配置而把全链路标为失败。

### 3.2 按目前的修改方向分为八类

分类服务于“为什么改、影响谁、怎么验证”，不等于八个 Agent，也不要求一轮做八类。旧补丁器明确区分 metadata、正文替换、模块插入、新页面代码等操作；这些是代码编辑形式，不是完整的 SEO 实验分类。下面细化当前方案的工作范围，不宣称旧系统已经可靠支持全部类别。[旧补丁器](/Users/shixianglong/Desktop/seo-agent/backend/agent/product_patcher.py:297)

| 类别 / primary_category | 修改对象 | 默认最小完整干预 | 影响与评估重点 |
| --- | --- | --- | --- |
| 搜索摘要 / metadata | title、meta description | 一个页面的一个摘要表达策略；优先单改 title 或 description | 默认保护整页；固定查询组 CTR 为可选主指标，页面总点击为保护指标；核实实际搜索展示，不能只看源码 |
| 内容价值 / content | 解释段、使用步骤、真实例子、FAQ、事实、配套图片 | 解决一个具体用户问题的完整模块；可以含小标题、段落和必要配图，不按字数或文件数切碎 | 默认保护整页；相关查询组点击、页面总点击及可用的合格转化；不能只数新增关键词 |
| 页面结构 / structure | H1/H2 层级、段落顺序、目录、信息呈现位置 | 一段明确的阅读/查找路径调整，默认保持事实与主要文案不变 | 默认保护整页；搜索与可用的任务行为指标分开；若同时改写内容或 CTA，必须声明组合，不能只归因于层级 |
| 内链关系 / internal_links | 来源页、目标页、锚文本、链接位置 | 一组预先列明的“来源页→目标页”关系，例如从相关教程补齐某工具页入口 | 来源页和目标页均进入影响集；观察目标及相关页面组总量，防止流量只是站内重新分配；导航/页脚按实际覆盖页面扩大 |
| 结构化数据 / structured_data | 与可见内容一致、当前受支持且符合资格的 Schema | 一个实体或关系图的完整表达；必要的 @id、引用和属性一致性一起处理 | 校验语法、事实、资格及实际展示；有效标记不等于必然展示或排名改善 |
| 抓取与索引 / crawl_index | 状态码、canonical、robots、noindex、渲染、Sitemap、hreflang | 一个已定位根因及其必要依赖修复；策略性调整另立优化或结构项目 | 工程检查优先，搜索恢复另记；影响可能是一页、URL/语言组或全站，不能因只改一行而视为低风险 |
| 性能与体验 / performance | 图片、脚本、加载策略、布局稳定性 | 一个有诊断证据的瓶颈及必要改动组合，例如首屏图资源与加载方式 | 检查实际受影响页面/设备；可重复实验室测试与可用的真实用户数据分开，性能改善不直接等于 SEO 收益 |
| 页面生命周期 / page_lifecycle | 新页面；另行授权的合并、迁移、下线 | 一个搜索意图对应的完整上线或迁移包，包含必要路由、canonical、Sitemap、入口和跳转 | 新旧 URL、来源页、同意图旧页都要检查；评估意图组净变化，不能把新页从零增长全算新增收益 |

类别不是互斥的物理位置：H1 改词主要属于内容，H1 层级/位置调整主要属于结构；canonical 虽在 head 中，主要属于抓取与索引。指定一个主类别，同时记录跨类别的必要配套项，禁止通过改类别名绕过历史或观察锁。

Google 会综合 title、主标题等来源生成标题链接，摘要也可能取自正文并随查询变化。因此“不同 HTML 字段”不意味着搜索效果相互独立。[标题链接](https://developers.google.com/search/docs/appearance/title-link)、[摘要](https://developers.google.com/search/docs/appearance/snippet)

结构化数据必须符合内容和资格要求，验证通过也不保证富媒体展示；URL 迁移则需要协调映射、跳转和相关站点信号，不能为坚持单字段实验而故意留下不完整迁移。[结构化数据规则](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)、[URL 迁移](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)

首轮默认不做批量新页面、全站模板重写、URL 迁移、自动删页、域名变更、自动购买外链。它们不是永远禁止，而是超出小范围 SEO 实验，需要单独立项和影响评估。登录、支付和业务权限逻辑不因 SEO 提案而顺带修改。

这里需要纠正此前的 FAQ 示例：Google 当前更新记录说明，FAQ 富媒体结果自 2026-05-07 起不再展示。因此“加 FAQ Schema 来获得 FAQ 搜索展示”不能作为现行收益假设；FAQ 正文是否有用仍取决于用户需求。该例也说明经验规则必须保存来源和复核日期。[Google 官方更新](https://developers.google.com/search/updates)

### 3.3 先判工作性质，再决定是否做实验

| 工作性质 / work_kind | 判断标准 | 如何完成与记忆 |
| --- | --- | --- |
| 修复 / repair | 有可验证的错误和正确性依据，例如错误 noindex、断链、过时产品事实 | 按权限一次修正根因及必要一致性；先验收错误消失。允许没有 GSC 数据时完成工程修复，但 SEO 影响记 unknown；相关旧实验标污染/中断，不让实验锁阻止必要事故处理 |
| 优化实验 / experiment | 现状可以正常使用，某种调整可能更好，但效果不确定 | 预注册假设、范围、指标与观察条件；需要样本可行性。无数据不为了产生改动而反复猜文案 |
| 结构性项目 / structural_project | 新页、迁移、整组模板等有不可分割依赖和较大影响的工作 | 单独立项、风险审查、完整上线验收；需要时按完整页面组分批上线。之后观察整体结果，不假装每个子改动是独立实验 |

这三种性质与八个修改类别是两个维度：补齐缺失 title 可以是修复，改写有效 title 可以是实验；canonical 的正确性修复与规范化策略迁移也不是同一种任务。已知错误必须有事实依据，不能把“我觉得文案不好”标成 repair 来豁免门禁。单純内部重构且无可见内容、语义、可访问性或性能影响，不计 SEO 干预；仍核实影响并保留普通发布记录。

以上是项目设计策略，不是 Google 规定的分类。用同一账本保存三种工作，不另建三套 Agent 或数据库；修复与结构项目不必为完成工程验收强行填 CTR 判胜条件。

### 3.4 一次修改范围的四个边界

范围原则：**一个明确问题 + 最小完整干预 + 必要依赖闭包 + 可解释的评估范围**。文件数和代码行数只辅助评审成本，不能定义实验单位。

1. **干预边界：要验证/修复什么。** 写一句具体问题与预期机制，不接受“整体提升 SEO”作为范围。例如“补齐用户无法找到的导出操作说明”。
2. **编辑边界：哪些允许改。** 分列主改动、必要配套、禁止顺带做的事。配套项须回答“去掉这一项，主要改动还能正确上线并使用吗？”若可以，而且它有独立收益假设，通常应拆出；同为“提升转化”不是合并理由。
3. **影响边界：上线后实际改变谁。** 枚举页面、组件消费者、链接两端、语言/URL 关系和查询意图集。公共文件不必然影响全站，但必须以依赖分析和渲染差异证明真实范围；未知范围不能按单页批准。
4. **评估与保护边界：看哪些结果、暂时不许改谁。** 明确处理组、对照、查询组、主要指标和保护指标。默认冻结受影响整页及相关共享影响，对照也保护；仅改 title 仍不能在同页观察期间另改正文。

内链不沿整个站点图无限递归锁站：先覆盖直接来源/目标及有具体传播风险的模板或意图组；对更远影响记录不确定性。如果无法说明对照未受影响，换对照或降级为描述性分析，不能声称已完全隔离所有 SEO 影响。

### 3.5 如何决定合并还是拆开

- **单点可独立完成且数据足够：** 优先窄实验。例如只验证 title 的某一种表达，不顺带改 description、首屏和图片加载。
- **完成一件事必须联动：** 一起做并记一个完整干预。例如导出说明需要小标题、步骤、示意图及模块样式，涉及四个文件仍可是一项内容改进；同步改首页 title 不属于配套。
- **多个独立优化想一起做：** 默认拆开或择一。确有业务时限、样本限制等理由时，可以重新批准为组合干预，明确牺牲分项归因；数据不足并不自动意味着组合值得做，也可以 no_change。
- **已知错误/结构性上线：** 按正确性和依赖确定完整包，不为单变量拆出半成品。可分批的是相对完整的页面组，不是先上线新 URL、下一轮才补必要跳转。

组合方案即使上线后增长，也只能评价该组合，不能分别记录“标题有效、FAQ 有效、Schema 有效”。如果之后要知道某一成员的独立贡献，需要新的、有价值且可测量的设计；不默认把稳定组合拆开轮流试。没有结论时也不能自动对每个成员轮番微调。

这里采用的是减少干扰、尽量可解释的观察性/准实验设计，并非严格随机实验。搜索需求、竞争、算法和展示选择不能由我们固定；“只改一项”也不能保证因果归因。

第一版建议只开放低风险、边界明确的 metadata 或单个 content 模块试点；必要修复按既有权限处理。内链组、结构、Schema、性能在证据和影响检查齐备后开放；新页和迁移保持后续阶段单独立项。优先级依据真实问题，不规定所有站点必须先改 title。

## 4. 将一个大 Loop 拆为四种任务

这里拆的是工作阶段与触发时机，不是四个 Agent。同一个 Codex 按顺序执行需要的阶段；不要每天都完整跑“研究→生成→修改”。只在有事件或足够新数据时进入下一步。

| 任务 | 触发 | 工作内容 | 必须落盘的结果 | 可否修改网站 |
| --- | --- | --- | --- | --- |
| Observe：观察 | 数据刷新、部署事件；试点可每天一次 | 更新数据、查线上状态、找异常、对账人工改动 | snapshot、incident、下次检查时间 | 否 |
| Decide：决策 | 新机会、观察结果到期、已核实的问题 | 读完整相关记忆；选候选；必要时并行研究；立一个实验 | no_change / blocked / experiment_spec | 否 |
| Execute：执行 | 实验通过历史与资源门禁 | 编码、测试、自检；需独立复核时再委派或交人工；有发布授权才部署 | diff、checks、release、真实版本记录 | 仅批准范围 |
| Evaluate：评估 | 数据完整且到约定日期 | 检查暴露和污染、计算结果、审查解释、更新经验与限制 | assessment、页面状态、下一步 | 否；回滚另建关联动作 |

生产错误修复有独立 Incident 通道：发现服务错误、错误 noindex 等，按已有事故权限及时处理，并将相关 SEO 实验标记为中断或污染。不能为了保持实验纯净而保留错误页面。

一个任务完成后允许退出，下一次从账本恢复。数周的实验依赖可持久化调度记录唤醒任务，不依赖某个聊天一直运行；本次只设计调度，不创建自动化。

## 5. 单 Agent 串行优先，Codex 决定是否委派

### 5.1 最小结构

| 部分 | 工作 | 边界 |
| --- | --- | --- |
| 一个主 Codex | 串行研究、决策、编码、自检、解释评估和组织记忆；必要时分派子任务 | 主任务对最终结果负责；阶段切换不创建新 Agent |
| 工具与账本 | 数据采集、指标计算、完整历史查询、资源预约、状态恢复 | 程序执行硬性检查；不依赖 Codex 自报“检查通过” |
| 发布入口 / CI | 构建检查、发布准确版本、保存线上回执 | 发布身份与代码编辑权限分离；不是一个额外的 LLM Agent |
| 可选子 Agent | 独立的只读研究或第二视角审查 | 完成限定任务后返回主任务；没有独立生产发布权 |

本文及配套文档中 Builder、Reviewer、Evaluator 表示编码、检查、评估职责，默认可由同一个 Codex 分阶段承担，不代表必须启动独立 Agent。只有明确标为“独立复核”的情况，才需要另一个未参与起草的审查者或人工。

串行执行也可以并发调用互不依赖的数据工具，这不等于启动多 Agent。跨周复盘可由下一次 Codex 任务读取同一账本继续，不要求保留同一个模型进程。

### 5.2 委派由主 Codex 决定

| 情况 | 默认选择 | 理由 |
| --- | --- | --- |
| 一个页面、一个小改动，后一步依赖前一步结论 | 主任务串行 | 交接成本高于并行收益 |
| 已经在观察、无新证据或只是刷新数据 | 不开子 Agent | 没有独立研究需求，避免重复分析 |
| 多组竞品/页面可独立阅读，能明确分开证据范围 | 可委派只读研究 | 分担资料量，主任务保留决策与历史上下文 |
| 关键判断存在互相矛盾的证据，或需要主动找反证 | 可委派独立复核 | 提供第二视角；不能用多数票替代证据 |
| 常规低风险改动，自动检查与主任务自检能够覆盖 | 不强制子 Agent | 自检可完成普通实验，但如实标记为 self |
| 触发既定独立复核条件 | 子 Agent 或人工复核 | 不得把同一 Agent 换一个提示词称作独立审查 |

是否委派的判断考虑任务独立性、资料量、风险、交接成本、预算及工具可用性。可预期地节省时间或增加有效复核时才使用；不能因为“流程走到研究阶段”就自动生成研究 Agent。

每次委派只记录简短理由、问题范围和预期返回结果；一期默认最多同时两个子 Agent，由主任务直接管理，不递归扩张队伍。子任务结束后主任务核验证据再继续，不能把未经核验的摘要直接当成发布依据。

子 Agent 默认只读目标代码和已授权证据；实验写入、记忆状态更新、生产发布由主任务通过统一工具串行发起。子 Agent 不可用时，普通任务继续串行；不能用“缺少子 Agent”作为整个项目无法工作的理由。

### 5.3 自检与独立复核分开记

每次检查保存 `review_mode = self | independent_agent | human`，以及检查对象的 commit/Diff 和证据。主任务编码后先重新对照冻结方案检查范围、事实、渲染与测试，不因单 Agent 模式而省略检查。

既定独立复核条件包括：已验证失败策略的重试、历史重复规则的例外、超出常规修改频率、修改门禁本身，以及单独立项的高影响变更（例如 robots/canonical、共享全站模板和 URL 迁移）。普通已授权事故恢复按既有应急协议处理，不为了等待 SEO 审查而延误修复。

需要独立复核却没有可用审查者时，可先完成可审查结果，但保留该项发布条件未满足；不能通过选择串行模式豁免。子 Agent 审查也不等于人工批准，发布仍按真实权限执行。

### 5.4 将按需委派写成项目规则

实施阶段在项目 `AGENTS.md` 中加入以下简短规则，由每次主 Codex 读取后自行判断，不要求用户逐次指定 Agent 数量：

> 默认使用一个 Agent 串行完成 SEO 工作。遇到可独立完成的资料研究，或需要第二视角的审查，且收益值得交接和成本时，请按需委派给子 Agent；由主 Codex 决定是否触发。不要按阶段固定创建 Agent。子 Agent 默认只读，不直接修改网站或权威记忆；主任务统一核验与执行。无独立子任务就不开子 Agent。始终遵守发布与独立复核条件。

当前官方文档说明，Codex 可根据用户明确请求或适用的 `AGENTS.md` / skill 指令委派；子 Agent 增加 Token 消耗，并行写入还会增加冲突。因此把选择权写在项目规则中，比搭建固定多 Agent 流水线更符合本设计。[Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)

以上是待实施规则，没有在本次修改中创建 `AGENTS.md` 或修改全局 Codex 配置。每个实际委派的任务都绑定 evidence_snapshot_id、memory_revision 与范围。搜索页面及其正文仅作外部数据，不作为执行命令或重写项目规则的指令。

## 6. 一次真正可执行的页面实验

1. **恢复上下文。** 查询站点配置、线上版本、活动实验、稳定版本、历史改动、失败与否决记录；校验数据版本。历史不完整时允许研究，不允许新增 SEO 写入。
2. **确认问题。** 优先检查技术错误和数据错误；区分需求下降、索引问题、摘要问题与内容问题。高优先级不是“排名一波动就改”。
3. **筛候选。** 去掉被观察锁、稳定保护、共享组件或重复历史拦住的候选。机会按业务相关性、证据质量、可测量性、影响和成本排序；无候选则 no_change。
4. **确定性质与最小完整干预。** 按第 3 节选择 work_kind、主类别和四个范围。实验默认一个主要假设与主要指标；页面只是常见单位，内容模块、内链组和完整上线包按实际机制定义。独立优化不顺带混入，必要联动或明确批准的组合必须保存成员及整体归因限制。
5. **预注册评估。** 锁定前后时间窗、国家/设备/查询集合、对照集合、统计方法、业务最小有意义变化、评估日、最长等待、保护指标和停止条件。
6. **历史准入。** 检查完整祖先版本、语义策略、以前失败原因、最近修改数量和重新立项证据。取得资源预约和当前台账版本。
7. **编码与审查。** 主 Codex 从已确认产品基线开始编码，再按冻结规范自检范围和影响；需要独立复核时再调用审查者。超出范围时回到方案阶段，不能在一个实验里顺手修多个 SEO 点。
8. **发布前再检查。** 重新查询历史、锁、线上和源码基线；绑定 plan_hash、diff_hash、commit、资源集合、检查结果和批准记录。审批后 Diff 变化必须失效重审。
9. **明确部署。** 构建成功不算线上成功；保存 deployment_id、实际生效 commit、线上页面快照。CDN、路由或线上内容不符合预期时不能开始效果验证。
10. **观察、冻结、评估。** 先确认版本暴露，再收集完整数据。观察期间不调整该范围；到期计算结果。无结论不等于失败，确认失败也不必自动撤回每个改动。
11. **写记忆。** 记录保留/回滚/重新立项/继续观察的决策及原因。下一轮最先检查这些限制，而不是重新生成一套偏好的文案。

## 7. 效果评估：防止把噪声学成经验

### 7.1 数据与口径

发现机会可以看较长历史，实验不能直接比较两个大幅重叠的滚动 90 天总数。保存逐日快照，用不重叠的前后窗口；周几分布匹配，季节性强时补历史同期。

GSC 请求明确记录日期、PT 时区、search type、过滤、维度、分页和 dataState；使用最终数据做结论。按实验目标定向拉取，并保存站点/页面总量和查询维度数据的口径差异。分页也不保证获得所有长尾记录；缺行不能自动当零，采集失败不能覆盖成功快照。[Search Analytics API](https://developers.google.com/webmaster-tools/v1/searchanalytics/query)

CTR = 合计点击 / 合计展现，不能简单平均各行 CTR。平均排名只用于同口径诊断和辅助分层，不单独代表业务胜负。固定查询集合同时保留页面总量保护指标，避免只看选中关键词、漏掉其他词的损失。

### 7.2 何时开始计时

分别记录 `deployed_at`、`live_verified_at`、`search_exposure_evidence_at` 和 `measurement_start_at`。

线上验证确认用户能看到新版本；Search Console 的最后抓取或采样 SERP 可以辅助判断搜索侧处理，但不能证明所有用户已看到同一个摘要。Google 可自动生成与 HTML title 不同的标题，并需要重新抓取和处理。[Google 标题链接说明](https://developers.google.com/search/docs/appearance/title-link)

因此应预先设定搜索处理缓冲期、暴露证据要求和等待上限。标题测试若采样仍是旧标题，先判断处理延迟/标题重写，不立刻再改文案；没有足够暴露证据时记录 exposure_unknown，不伪造确定的生效时间。固定复查时钟从 live_verified_at 起算；搜索处理状态影响结论和分析窗口，不向后重置第 20/40/60 天的复查时钟。

### 7.3 统一复查周期与样本

统一按部署确认后固定间隔复查，而不是按类别配置不同的首次复查日。默认 `SEO_REVIEW_INTERVAL_DAYS=20`、`SEO_REVIEW_MAX_CHECKS=3`，对应第 20/40/60 天；这是用户选定的管理节奏，不是 Google 保证或统计判胜阈值。

| 时间 | 动作 | 禁止误解 |
| --- | --- | --- |
| 部署当天 | 确认真实版本、工程验收、保存 live_verified_at | Build 成功不等于上线成功 |
| 检查点之间 | 保持影响范围冻结，处理监控告警、数据异常和有权限的必要修复 | 不因没到复查日而保留故障，不反复改文案 |
| D×1 / D×2 | 核实搜索处理、最终数据、样本和干扰，输出保留/修复回滚/继续观察/无结论 | 到期不等于一定能判断成败，也不自动开启新优化 |
| D×N，默认第 60 天 | 最后复查；仍不足以判断则关闭为 inconclusive，保留正确且无已知损害的版本和重开条件 | 不是宣布 SEO 无效；部署未知/事故未恢复必须先对账，不自动解锁 |

管理项目 `config` 保存上述明文变量，可提交 Git，由 [seo_context.py](../skills/seo-front-loop/scripts/seo_context.py) 显式读取；当前进程环境优先，其次 `config`，最后默认值。凭据不放进 config。配置与来源进入立项快照；已部署实验使用冻结的 `review_policy`，调变量不追溯改变旧任务。用户明确调整旧计划时记前后值、理由和授权，不覆盖原评估。最长等待为冻结 D×N，默认 60 天。

技术修复仍立即验收；内容、内链、新页等在统一检查点可以得到“暂时无法判断”，不为满足 20 天而捏造效果。新页面没有自身历史基线，检查意图组净变化，不套旧页面 CTR 前后比较。Google 说明效果可能需要数天到数月且不保证收益，因此最晚结案是资源管理决定。[Google 流量变化诊断](https://developers.google.com/search/docs/monitor-debug/debugging-search-traffic-drops)

基线可先考虑此前 28 天，但最终按实验噪声和口径固定，不要求机械地把部署前后 20 天总量直接比较。保持星期组成可比、记录搜索处理缓冲及实际数据截止；第 20 天数据不完整则使用可用最终数据并明确缺口，不能填零。错过多个检查点只做一次当前复查，补记漏检，不伪造历史报告。

不使用“500 或 1000 次展现即可判胜”这一固定规则。例如基础 CTR 约 1% 时，1000 展现约对应 10 次点击，通常不足以识别小幅改善。应在立项时用历史波动、基线率、最小有意义效果和可接受不确定性判断该实验是否测得出来；测不出来就选择更有数据的页面、延长观察或明确只验证工程结果。

### 7.4 对照、统计和结论

优先选择干预前走势接近、同类型、无共享改动的页面或页面组作对照；先固定对照，不能看结果后挑一个下跌页面衬托收益。记录算法更新、促销、产品发布、品牌活动、需求变化等混杂因素。

有合适对照和足够日级样本时，使用预先固定的趋势/对照分析，并考虑时间相关性；可将按周区块重采样的区间或其他适用估计器写入测量协议。方法由程序计算并版本化，Evaluator 不凭文字“信心”产生置信区间。平行趋势不可信或样本太短时不强行做因果估计。

默认只在预注册评估日作效果判断，日常检查只监控技术和预定义保护指标；不每天看 p 值直到某天通过。保护指标告警也按既定规则解释，不能把自然波动当自动回滚理由。扩大到多个实验时要处理多重比较，而非只汇报获胜的那个。

同一实验第 20/40/60 天的累计窗口可能重叠，不能视为三份独立验证。若在多个检查点进行正式判胜检验，需预先选择处理重复检验的方法；否则限定为描述性/有局限的运营判断，不因多看几次而升级因果强度。Skill 目前只算到期日期，不计算统计显著性。

同时保存两个字段：

- `observed_result`：positive / negative / no_detectable_difference / insufficient / contaminated。
- `causal_strength`：descriptive / suggestive / supported，并附方法与限制。没有对照不自动归零，但通常只能描述相关变化。

操作决策单独保存：retain / rollback / extend / close_inconclusive / reopen_proposal。无明显收益但内容正确、没有损害时，可以保留当前版本并停止折腾；不要把“没有显著改善”误写为“无效且必须撤回”。

## 8. 必须提前处理的问题

| 问题 | 典型后果 | 处理方式 |
| --- | --- | --- |
| A→B→C→A 或近义改写 | 循环消耗，无法积累观察 | 完整版本图、语义策略历史、重新立项证据、频率限制；详见记忆协议 |
| 多 Agent 或多个任务同时修改 | 相互覆盖、重复发布 | 统一记账服务、原子资源预约、单写入者；不能只依赖进程内锁 |
| 公共模板影响多个页面 | 一个页面改动污染对照和其他实验 | 页面+共享资源+查询集群影响图；不明范围按大范围保守阻断 |
| 修改和部署不同步 | 对旧版本测出“新版本效果” | 部署回执、线上指纹、缓存检查、观测起点分离 |
| 人工/其他系统绕过流程 | 台账与实际网站失真 | 上线对账和 drift 事件；暂停相关实验，不自动覆盖人工代码 |
| 只记最近几条或摘要漏信息 | 很久前失败的 A 又被提出 | 历史门禁查询全部关联版本，摘要不能替代它 |
| 数据不完整或口径变化 | API 失败被当成流量暴跌 | 质量状态、时间窗和过滤契约；缺失不填零 |
| 季节性/排名/设备结构变化 | CTR 增长被错误归因 | 分层、固定集合、对照、外部事件标注 |
| 搜索结果样式变化、点击被分流 | 排名相近但点击下降 | 保留 SERP 快照和展示特征，不能一律归咎标题 |
| 一个 Query 对应多页面 | 相互蚕食或本来就是合理覆盖 | 看意图与站点合计；多个 URL 本身不是自动合并理由 |
| 新页面无历史、低流量 | 强行套用单页前后实验 | 单独协议；允许不可判定，不用模型编造结论 |
| 模型事实幻觉/复制竞品 | 虚假功能、价格、效果承诺 | 产品事实库与来源核验；不虚构评价、检测通过率、认证或使用效果 |
| 旧 SEO 规则失效 | 反复做无收益 Schema 等工作 | 规则有来源、适用条件、checked_at、失效/复核触发条件 |
| 成功经验被过度推广 | 一个页面偶然涨，所有页面照搬 | 单页经验先局部保留；多次可比独立验证后再审查推广 |
| 错误版本被永久锁住 | “不能再改”阻止真正修复 | 允许事故修复和有证据的重新立项，所有例外留痕 |
| 只优化点击不管转化 | 引入不相关流量和误导摘要 | 业务相关性与转化保护；归因未接通就承认看不到 |
| 反复研究相同证据 | Token/API 花费上升但无新信息 | 按证据内容、问题及模型/提示版本缓存；预算到顶暂停当前阶段 |
| LLM 的多数票 | 共同错误看似共识 | Reviewer 找反证；重复引用同一来源不能当多份独立证据 |
| 整站回滚覆盖别人的改动 | 修 SEO 时丢失后续业务发布 | 逆向补丁以当前 HEAD 为基线；冲突转人工处理，禁止盲目还原旧快照 |
| 外部内容包含指令或敏感查询 | 提示注入或泄露 | 外部证据只作数据；查询脱敏/聚合；密钥留在连接器执行环境 |
| 休眠、断网、崩溃、备份丢失 | 跳过状态或重复部署 | 持久化任务、幂等键、恢复对账、私有备份和恢复演练 |

| GSC、PageSpeed、CrUX 连接器 | 数据工具 | 增加显式时间窗、分页、质量标记；重用鉴权方式，不复制秘密 |
| 站点爬虫、SERP/竞品采集 | 证据工具 | 增加不可变快照、内容摘要、来源和请求配置；不要保留“必须每维都分析”的门槛 |
| SQLite/Evidence Packet/记录 | 记忆服务基础 | 版本化迁移；旧结果标 legacy_unverified；缺部署证据的历史不能直接当有效实验 |
| Dimension/Strategy/Execution brains | Codex 任务协议 | 提炼输入输出和限制，不迁移大量固定 LLM 调用链 |
| Product Patcher | Codex Builder | 用实际代码理解和 Diff 取代正则；小工具只在通过样例验证后保留 |
| Safety/Build/Rollback | CI 与发布适配器 | 保留规则意图，重测实现；Build、部署、线上检查必须分别可验证 |
| Validation/Attribution | 调度与评估器 | 重做窗口、暴露、污染与结论分级；不能直接沿用指标计票 |
| 管理后台 | 初期 Markdown 报告+实验列表 | 先不重建 React 控制台；证明流程有用后再决定 |

切换前要核实旧系统是否运行、有无未结束实验及谁在发布。生产写入交接必须是同一站点只有一个发布所有者；本设计不授权现在关闭服务、迁移秘密或修改线上网站。

第一阶段仅用脱敏静态快照做回放，并用旧系统产出作参考，不执行旧 `run_growth_loop`，避免它包含的自治调用产生副作用。

## 10. 实施次序与退出条件

1. **P0：建立可信基线。** 确认目标域名、产品代码路径、GSC property、部署流程、运行状态目录；盘点已发生改动。路径与站点映射不确定时停在只读研究。
2. **P1：先实现记忆与门禁。** 完成账本、查询、资源锁、防重复、发布对账、恢复；通过 [执行手册](RUNBOOK.md) 中的关键失败场景。没有这一步，不开放自主修改。
3. **P2：只读试运行。** 先验证单 Codex 串行能完成整轮，并与旧系统参考产出比较证据正确性、重复提案、范围偏离和成本；只有出现具体研究瓶颈或独立复核需求时，才追加子 Agent 对照，不强制为验收启动多 Agent。
4. **P3：一个真实实验。** 选有足够数据且无活动改动的页面，生成 PR，按既有授权发布，等待完整观察窗；验证记忆跨任务恢复和“不再改动”行为。
5. **P4：有限扩大。** 多个不共享影响范围的页面小规模试点，默认最多 3 个活动实验；仍然每次最多启动一个。是否扩展由记录质量与实际结果决定，不由固定日期决定。

P1 的验收重点是程序可靠性，P3/P4 才涉及 SEO 结果。完整实施后也不承诺排名增长，但可以要求：可追溯、可停止、可恢复、能识别证据不足，并用相同协议评估是否真的产生增益。

第一版不建设向量数据库、Agent 管理平台或复杂自动学习。优先完成“查历史→拒绝重复→部署对账→正确评估”四件事。
