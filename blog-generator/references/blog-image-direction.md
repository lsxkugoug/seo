# Blog 配图适配

这是 Blog Generator 写作阶段内的配图要求：从当前文章 brief 和既有网站样式继续工作，产出随文章使用的图片。无需另建项目、另开设计任务、增加交互选择器或要求用户逐篇确认设计方向。它不代替选题、事实、正文查重、内链和发布检查，也不授权上传、发布或替换历史文章图片。

方法来自 [create-quiet-humanist-designs](https://github.com/pepperliu722-sudo/create-quiet-humanist-designs)，参考版本 `54e5794b2d1ee5536343eb2d6fe6413c776c9485`。这里保留“内容 → 主体/动作/痕迹 → 多方向比较 → 媒介适配 → 验收”的方法，并针对网站阅读场景重新组织；无需另外安装该 Skill。

## 1. 适配现有网站，再决定图片用途

先确认网站已经如何展示文章：主图位置、卡片比例、背景色、文字层级、图片裁切方式及手机布局。图片应融入这些现有位置，不为配图新增页面、功能、宣传语、导航、切换按钮或新的阅读步骤。最终交付仍是原来的 Blog 文章及其图片字段；制作本地审阅效果图时也只展示现有页面承载配图的效果，不把设计说明做成网站产品功能。

配图服务文章的阅读气质、主题关联和视觉连贯性。适合时可表达一个动作或关系，但不要求每张图都独立讲完文章、给出完整结论或形成一套海报叙事。

| 用途 | 应完成的工作 | 不应承担的工作 |
| --- | --- | --- |
| 封面 / 列表图 | 让读者辨认文章主题、情境或取舍，形成有区别的视觉入口 | 重复整段标题、假装产品实测、塞满正文知识点 |
| 正文解释图 | 解释一个确实需要视觉表达的步骤、变化、对照或关系 | 只为凑数量、装饰每一个 H2、代替关键答案 |
| 产品截图 | 展示核实过的真实界面和操作状态 | 生成虚构 UI、虚构分数或功能证明 |

Humanizer 的网页已有独立 HTML 标题和摘要，封面默认不再烘焙完整标题、Logo、按钮或 URL。主图是现有文章的一项资产，不是新的页面组合交付。独立海报属于用户另行提出的任务，不在 Blog 默认流程内。不能把原设计 Skill 的海报要求机械搬到 Blog 图片里。

正文没有需要解释的视觉任务时，只做一张主图即可。需要正文图时先核实当前渲染器和发布契约支持的格式；不为了这份规范改后台、数据库、Markdown 渲染或 API。暂不支持则交付图片、图注和插入位置建议，不把未经支持的语法发到正式正文。

## 2. 从文章提炼画面，不从风格词开始

读已批准的 brief、开头、核心例子与结论。用两三句话说明：读者在处理什么，做什么判断，什么变化值得看见，什么不能被画面误解。

Agent 可在内部快速比较两三个适合当前页面的方向，例如真实工作情境、可辨认的物体动作、精确的机制类比；按本文需要选择，不额外要求用户做一轮方案选择。需要表达动作时，可用一句话澄清：

> [具体主体] 正在 [动作]，通过 [一个线索] 留下 [可见变化]，使读者理解 [本文的具体意思]。

文章涉及人的判断、选择、作者与工具关系时，可以比较一个具有明确行为的人物方案与一个非人物方案。人物必须在做事，不能只是“桌边微笑的人”；也不要把每篇变成同一个小人或机器人。

选择最适合现有页面、与本文协调、在缩略图里清楚且不与近期图片雷同的方案。比较只需内部简短判断，通常生成一张合适的图，不默认输出独立设计提案或多套效果图。

把图片放回现有文章标题与摘要旁判断：它是否协调、是否给读者适当的主题或情境线索、是否抢占文字注意力。遮住标题可辅助发现过于通用的图片，但不是“必须单看图就读懂文章”的门槛。纯装饰也应有本站视觉和本文情境依据，不能仅因图片漂亮就使用。

## 3. Humanizer 编辑插画方向

仅用于明确选择 `humanizer_editorial` 的项目或用户指定的 Humanizer 工作。其他网站按自己的品牌和场景选择，不能继承 Humanizer 的色彩与学生情境。

目标：理性、有人在思考、清楚但不冷硬；尊重写作中的判断，不把 AI 描绘成自动保证正确的魔法。以当前网站的明亮底色、清晰标题和蓝色品牌环境作适配依据，不把一次观察当成永久品牌规范。

- 优先尝试有辨识度的编辑插画：有选择的墨线、局部铅笔修订痕迹、平涂印色、少量纸材拼接或刻意简化的物体。材质要跟随物体，不把整张图片盖上脏旧滤镜。
- 一张图保持一个视觉重点。需要表现动作时配一两个线索即可，不强迫所有配图都成为解释图。留白服务主体并配合现有卡片；避免物件、小图标、箭头平均铺满画布。
- 保持两三项一致性即可，例如克制的线条、清楚的图地关系、局部印色。每篇允许更换主体、材质、明暗和构图。
- 蓝色可作为本站识别色，但不是每张都必须蓝白。可以由内容选择冷灰、浅暖白、淡粉、绿色或深色小区域；避免连续重复“奶油纸 + 蓝色纸片 + 珊瑚红点”。这些颜色是选择空间，不是固定模板。
- 每张保留一个有理由的视觉变化：意料之外的尺度、边缘裁切、错位、局部覆盖、一个被保留的修改痕迹。不要同时把所有元素都画得古怪。
- 学习、咖啡、桌面、风景可以出现，但必须有本文情境或动作的理由；不能仅因它们“治愈”就替代内容。纸张、剪刀、放大镜也不是禁用物，只是不自动等同于“写作”“精简”“核查”。

避免惯用的发光 AI 脑、机器人握手、霓虹电路、漂浮玻璃、塑料 3D 和图库式摆拍。也避免另一种模板：漂亮物体放在中央，配一层纸纹，换标题就当新图。

### 真实性边界

说明性插画可使用隐喻，但不能冒充实际产品效果、用户证言或研究证据。检测类文章不使用“100% human”“绕过检测”、通过印章或虚构仪表数值暗示保证；比较类文章不生成竞品界面/Logo 作为测试证据。需要真实界面时使用已核验截图；需要准确数字、标签、引文或流程箭头时，用可编辑排版或矢量工具精确制作并与来源核对。

## 4. 连续文章的差异化

先看当前能取得的近期 6–12 张图，以及最相近主题的配图；记录实际看了哪些，资料不足就如实写明。不要声称已经视觉核对全部历史。

比较主体、动作、构图、材质、色彩重心和叙事方式，指出最近最常出现的习惯。新图至少改变重复最明显的两项，其中一项应是动作、主体或语义关系，而不只是换色/换裁切。

- 相同咖啡桌换 URL、相同图片换文件名，仍是重复。
- 相邻主题全是“两页纸加红笔”，即使像素不同也要重新比较方案。
- 统一的是识别感和阅读质量，不是同一版式轮换物件。
- 图像视觉差异不能证明文章内容独立，仍执行原来的正文级查重。

逐篇唯一 URL 规则保留。若能取得历史原图，可补充文件哈希或感知相似性检查；这些只能辅助人工/Agent 的视觉比较，不承诺现有脚本已实现视觉去重。

## 5. 生成、摄影与托管

尊重项目已有策略。旧 `search_per_article` 继续检索授权图片；`generate_or_search_per_article` 可以优先生成编辑插画，必要时选授权摄影。生成工具不可用时，不要求安装某工具、购买 API 或改变执行环境才能继续写作。

生成分支：保存内容 brief、方向选择、最终提示词、实际可知的工具/版本、时间和原始文件；拿不到模型版本就写未知，不猜。不得为生成图伪造摄影师、素材库页面或版权归属。使用用户提供素材时遵守其许可；不直接复制参考图的构图或特征角色。

摄影分支：保存来源页面、作者/摄影师、许可依据、检索词和稳定直链。可沿用 Pexels 等项目允许的来源；不是看到 URL 就视为授权成立。真实截图注明页面、时间和必要的隐私处理。

预览与生产状态分开：`preview_only`、`asset_ready`、`hosted_verified` 是运行记录中的描述，不是新增 API 枚举。只有本地文件时属于预览或资产完成；只有经已有获准的存储流程获得稳定 HTTPS 图片 URL、检查实际响应为图片且内容一致后，才能作为发布主图。没有上传能力时可保留草稿、尝试已有获准的素材来源，最终不合格才按原规则阻断发布。

不得把本机路径、`data:`、`blob:`、随机重定向端点或会过期的预览链接当生产图片 URL。不得借“生图”修改鉴权、发布开关、定时任务或生产存储权限。

## 6. 网页尺寸、可读性与性能

先核实页面实际容器与 `object-fit`，不要假定所有卡片都是 16:9。2026-10-29 抽查 Humanizer 桌面列表，精选图区约 658×256、普通卡片约 427×192，使用 `contain`；以后以实际页面为准。仅改图片不能保证消除现有容器留边，不擅改前端来美化预览。

在没有更具体站点约定时，可用约 2:1 的横向图作为 Humanizer 候选主稿，例如 1600×800；这是导出建议，不是发布契约新增硬门槛。画面的主体和动作放在中部约 80% 的区域，边缘可裁剪而不损失关键关系。不能靠图片内的小字来解释主题。

检查实际卡片的 `contain` 呈现、可能的 16:9/宽卡裁切、约 320px 宽的缩略图及手机呈现。封面之外的正文示意图采用适合信息的比例，不强制横向。

导出站点支持的 WebP/AVIF/JPEG 等格式，检查尺寸、体积、压缩后的线条与色块，不把生成器的大 PNG 直接视作网页最优输出。可把 120–300KB 作为普通封面的初始体积目标；若质量与体积冲突，记录理由，不为达标毁掉清晰度。示例预览允许保留原稿，未优化应明确标注。

替代文本描述画面中确实可见的主体、动作和关系，不堆关键词、不照抄标题、不把概念解释写成未经证明的结果。说明性隐喻必要时用“illustration”表明性质。若当前接口/模板没有展示独立 alt 字段，记录缺口，不仅凭 payload 声称可访问性已完成。

## 7. 生成提示词骨架

先填写内容判断再整理成提示词；这段是生成指导，不是绑定某个服务的参数 schema：

> 为 [站点/读者] 的 [文章任务] 创作横向 Blog 编辑插画。真实意思是 [核心观点及边界]。画面显示 [具体主体] 正在 [动作]，以 [线索] 留下 [痕迹/变化]。采用 [两种有依据的制作方式]，通过 [一个构图决定] 让该关系在缩略图可辨。背景与 [当前网站环境] 协调，主体保持清晰；比例 [已确认用途]。不要生成标题、Logo、按钮、水印、假数据、伪 UI 或可误认成事实的效果承诺。与近期 [实际观察到的重复习惯] 拉开区别。

如果涉及文字证据，把准确文字留给页面或可核验的后期排版；生成图中用简洁的抽象文字行提示文稿，不用伪字母段落冒充真实证据。

## 8. 随文章完成检查与交付

不扩充原候选输出 YAML 或后端 payload，不引入独立设计交付包。正文和图片作为同一篇 Blog 交付，来源、提示词与 QA 简要附在这篇文章已有运行记录的配图项内：

- 现有图片位置与尺寸约束、所选画面与文章的关系；只有判断需要时才记录其他候选方向。
- 与近期图像的具体差异、参考范围和覆盖缺口。
- 图片来源与生成/授权信息、本地文件、可用时的托管 URL。
- 画面 alt、图注（需要时）、尺寸/体积、裁切说明。
- 语义、真实性、重复、缩略图、移动端、技术访问性各项的通过/失败/未测状态。

审核时回答：图放进现有网站是否协调？是否服务当前文章而不抢正文？是否误示产品能力或效果？缩小后主体仍清楚吗？和近邻文章是否雷同？来源与上线 URL 能核验吗？现有文字和交互是否保持原样？

未满足者明确列为待处理；不能拿“艺术评分高”抵消失实或失效 URL。生成后先做一轮检查，有具体问题再做定向修订；普通单图最多再尝试两次，仍不合适就保留方案/选择允许的授权图片，不无限生成。图片选择失败不丢弃已完成正文；正式发布仍受原有全部门禁约束。
